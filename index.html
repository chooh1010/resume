문제 해결 사례 1

애플리케이션 Scale Out

문제 상황

500명의 가상 사용자가 요청하는 환경에서 애플리케이션 서버 CPU가 약 200%에 도달했습니다. CPU가 포화되면서 요청이 처리 대기 상태에 놓였고, 응답시간이 크게 증가했습니다.

해결 방법

HAProxy를 로드밸런서로 사용하고 애플리케이션 서버를 1대에서 2대로 확장했습니다. 요청을 두 개의 애플리케이션 인스턴스로 분산하여 단일 서버의 CPU 포화를 해소했습니다.

"애플리케이션 서버를 확장해 처리량을 높였지만, 병목은 사라진 것이 아니라 MySQL로 이동했습니다."

HAProxy Docker Spring Boot JMeter Grafana

개선 결과 (Scale Out)

TPS 274/s → 527/s
평균 응답시간 867ms → 32ms
P95 응답시간 4,799ms → 93ms
P99 응답시간 7,511ms → 201ms
에러율 0% 유지

CPU 사용률 변화

BEFORE

애플리케이션 1대의 CPU가 약 200%에 도달하면서 요청이 처리 대기 상태에 놓였다.

AFTER

애플리케이션을 2대로 확장한 뒤 각 인스턴스가 요청을 분담하면서 CPU 포화가 해소되었다.

응답시간 변화

BEFORE

CPU 포화로 요청이 대기하면서 P95와 P99 응답시간이 크게 증가했다.

AFTER

요청이 두 인스턴스로 분산되면서 P99가 7,511ms에서 201ms로 감소했다.

문제 해결 사례 2

MySQL Read Replica

문제 상황

애플리케이션을 Scale Out한 뒤 MySQL CPU 사용률이 약 100%에 도달했습니다. 애플리케이션 병목이 해소되면서 단일 MySQL이 읽기와 쓰기 요청을 모두 처리하는 구조가 새로운 병목이 되었습니다.

해결 방법

MySQL Read Replica를 도입해 읽기와 쓰기 부하를 분리했습니다.

  • Master DB: 쓰기 요청 처리
  • Replica DB: 읽기 요청 처리 (읽기 트래픽 약 90% 분산)
  • 쓰기 직후 데이터 정합성이 필요한 요청은 일정 시간 Master를 조회하는 Sticky Primary 방식 적용

"Read Replica의 핵심 성과는 단순한 TPS 증가가 아니라, Master의 부하를 분산하고 응답시간을 안정화한 것입니다."

MySQL Replication Spring Data JPA LazyConnectionDataSourceProxy Grafana

개선 결과 (Read Replica)

평균 응답시간 32ms → 10ms
P99 응답시간 237ms → 80ms
최대 응답시간 1,338ms → 469ms
Master CPU 약 100% → 약 25%
TPS 증가폭 약 527/s → 약 539/s

* 테스트에는 500개의 고정 스레드와 Think Time이 적용되어 처리량(TPS) 증가에는 제한이 있었습니다. 따라서 응답시간 최적화와 Master 부하 감소에 초점을 맞추었습니다.

DB CPU 사용률 변화

BEFORE

단일 MySQL이 읽기와 쓰기를 모두 처리하면서 CPU 사용률이 약 100%에 도달했다.

AFTER

Master는 쓰기에 집중하고 Replica가 읽기 요청을 담당하면서 Master CPU가 약 25%로 감소했다.

응답시간(Tail Latency) 변화

BEFORE

단일 MySQL에서 읽기와 쓰기 쿼리가 경쟁하면서 Tail Latency가 증가했다.

AFTER

읽기 쿼리를 Replica로 분산한 뒤 평균 응답시간은 10ms, P99는 80ms까지 감소했다.

성능 개선은 코드를 변경하는 것으로 끝나지 않습니다.

측정 결과가 달라져야 개선이라고 판단합니다. 기술을 적용했다는 사실보다 실제 지표가 어떻게 달라졌는지를 중요하게 생각합니다.
