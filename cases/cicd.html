배포·모니터링 자동화

성능 개선은 "여러 번 빠르게 배포하고 검증"하는 반복 작업입니다.
수동 빌드·배포·상태 확인이 문제 해결 속도를 함께 늦추고 있어, 파이프라인 전체를 자동화했습니다.

STEP 1 · 문제 상황

수동 절차가 성능 개선 사이클 전체를 늦추고 있었습니다

빌드, 이미지 생성, 배포, 운영 상태 확인이 모두 수동이어서 코드 수정 후 반영까지 시간이 걸리고 실수 가능성이 높았습니다. 특히 이 프로젝트의 성능 개선 작업(캐싱, Scale Out, Read Replica)은 배포 → 부하테스트 → 지표 확인을 여러 번 반복해야 하므로, 수동 절차가 문제 해결 속도를 함께 늦추고 있었습니다.

또한 팀 단위 프로젝트라 "빌드 → 배포" 자동화만으로는 부족했습니다. PR마다 코드 품질과 테스트 커버리지를 자동 검증해, 기준을 충족한 코드만 머지되도록 하는 품질 게이트가 필요했습니다.

STEP 2 · 해결 방법

PR 품질 게이트 + 배포 자동화, 두 단계 파이프라인

배포 단계 (main push 시)

main push
  ↓
GitHub Actions
  ├─ JDK 21 + Gradle 캐시 복원
  ├─ Docker Hub 로그인
  ├─ ./gradlew jib
  │    └─ 이미지 빌드 → Docker Hub push
  └─ SSH → EC2
       ├─ docker compose pull app
       └─ docker compose up -d app
            └─ app 서비스만 교체
               (MySQL·exporter는 무중단 유지)

Prometheus → Grafana (배포 후 지표 관찰)

PR 단계 (품질 게이트)

검사 항목 기준 도구
테스트 커버리지 80% 이상 Jacoco → SonarCloud
코드 품질 Major 이슈 0건 SonarCloud (GitHub App)
코드 스타일 네이버 핵데이 컨벤션 Checkstyle

Jacoco XML 리포트와 Checkstyle 리포트 경로를 SonarCloud에 함께 전달해 한 번의 분석으로 두 품질 지표를 동시 검사합니다. 기준 미달 PR은 머지가 제한됩니다.

Jib — Dockerfile 없이, 저사양 환경에 맞춘 JVM 튜닝까지

jib {
    from { image = "eclipse-temurin:21-jdk-alpine" }
    to {
        image = "chooh1010/popping-community"
        tags = ['latest', timestamp]
    }
    container {
        jvmFlags = [
            '-XX:+UseContainerSupport',
            '-Xms200m', '-Xmx240m',
            '-XX:ReservedCodeCacheSize=64m',
            '-XX:MaxMetaspaceSize=128m',
            '-XX:+UseStringDeduplication', ...
        ]
    }
}

EC2 t2.micro(1GB)에서 MySQL·exporter와 메모리를 나눠 써야 하므로, 힙(200~240m)·메타스페이스(128m)·코드캐시(64m)를 세분화해 상한을 고정했습니다. 초기 힙을 200m으로 고정한 이유는 힙이 천천히 늘어나는 동안 GC가 과도하게 발생하는 것을 막기 위해서입니다.

Jib은 Dockerfile 없이 Gradle 플러그인만으로 레이어드 이미지를 만들고 Docker Hub에 push합니다. 타임스탬프 태그를 함께 남겨 특정 시점 이미지로의 롤백이 가능합니다.

STEP 3 · 운영·보안

노출 범위와 자격증명을 최소화했습니다

포트 바인딩 제한

app:
  ports:
    - "8080:8080"             # 서비스 포트만 공개
    - "127.0.0.1:8081:8081"   # Actuator: 로컬 전용

mysqld-exporter:
  ports:
    - "127.0.0.1:9104:9104"   # SSH 터널로만 접근

Actuator·exporter는 127.0.0.1 바인딩으로 외부 직접 접근을 차단하고 SSH 터널을 통해서만 접근합니다.

자격증명 관리

  • 배포 자격증명(SSH 키, Docker Hub 토큰)은 GitHub Secrets로 관리
  • Docker Hub는 계정 비밀번호 대신 권한 제한 Access Token 사용 — 유출 시 해당 토큰만 폐기
  • DB 비밀번호·AWS 키는 EC2의 .env에만 존재, Git 미포함 (.env.example만 커밋)

결과

코드 수정 이후의 수동 작업이 제거되어, main 머지만으로 배포가 완료되고 Grafana에서 배포 직후 지표를 바로 관찰할 수 있게 됐습니다. 이 개발-운영 루프가 이후 모든 성능 개선 사례의 "동일 조건 반복 배포 + 지표 검증"을 가능하게 한 기반이 됐습니다.

"배포 자동화는 그 자체가 목적이 아니라, 문제 해결 사이클의 속도를 높이는 인프라였습니다."

자동화된 배포·모니터링 루프 위에서 캐싱부터 Read Replica까지 반복 검증했습니다.
